# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Saraha is an anonymous-messaging app: users get a public profile (`/u/[identifier]`) where anyone (logged in or not) can send them a message with optional image attachments. Separately, logged-in users can hold two-way 1:1 conversations (`/conversation`). The repo has two independent npm projects, `server/` (Express API) and `client/` (Next.js). There is no root package.json and no test suite.

## Commands

Server (`cd server`):
- `npm run start:dev` — runs `node --watch src/main.js` with `NODE_ENV=dev`, loading `server/.env.dev`
- `npm run start:prod-local` — same with `.env.prod`; `npm run start:prod` runs under pm2 cluster mode
- `npm run format` — prettier; lint with `npx eslint .`
- `npm run gen:key` — generate a 32-byte hex secret for env vars
- Manual API testing: `server/public/http/*.http` (REST Client files) and `server/public/doc/api/` (swagger/postman)

Client (`cd client`):
- `npm run dev`, `npm run build`, `npm run lint`, `npm run typecheck`, `npm run format`
- Add shadcn components: `npx shadcn@latest add <name>`
- `client/CLAUDE.md` → `client/AGENTS.md`: Next.js 16 has breaking changes vs. training data; read `client/node_modules/next/dist/docs/` before writing Next.js code. That block is auto-regenerated by `next dev`.

Running both requires MongoDB and Redis reachable via `DATABASE_URI` / `REDIS_URI`. The client expects the API at `http://127.0.0.1:9090` by default (`NEXT_PUBLIC_API_URL` for browser calls, `AUTH_API_URL` for the NextAuth route); the client env is `client/.env.local`.

## Server architecture

Plain JavaScript ESM, Express 5, Mongoose, Redis, Zod 4. Imports use the package `imports` alias `#/*` → `server/src/*`. Each folder re-exports through barrel files (`_INDEX.js`, and `_EXPORT.js` at `common/`, `core/`, `common/middleware/`); module folders use `_INDEX.JS` (uppercase extension). Prefer importing from the barrels.

- `src/main.js` — applies `appConfig` (helmet, cors, rate limiter, morgan, json), mounts `appController`, then `globalErrorHandler`; connects Mongo + Redis before listening.
- `src/appController.js` — routes `/authentication`, `/user`, `/message`, `/conversation`; catch-all 404.
- `src/module/<feature>/` — `<feature>Controller.js` (Router + middleware chain), `<feature>Service.js` (business logic), `dto/` (Zod schemas).
- `src/core/` — env config (`config/configEnv.js`, the only place `process.env` is read), Mongoose models, Redis client and key builders (`database/redis/keyCache.js`), and generic repository helpers (`database/repo/databaseRepo.js`: `find`, `findOne`, `findById`, `create`, `findOneAndDelete`, … all taking `{ model, filter, select, options }`). Services call these helpers rather than models directly.
- `src/common/` — exceptions, response handlers, middleware (guards, validation pipe, rate limiters, Redis-backed login-attempt/profile caches, multer upload), security (bcrypt hashing, encryption, JWT), mail + `emailEvent` (an EventEmitter that runs queued send-email callbacks asynchronously), enums.

### Conventions that span files

- **Errors**: `XxxException({ messageCode, extra })` in `common/exception/` *throws* immediately (via `ErrorResponse` → `new Error(msg, { cause: { status, messageCode, extra } })`); `throw X(...)` and bare `X(...)` both work. Express 5 forwards async rejections, so controllers don't wrap in try/catch. `globalErrorHandler` maps `cause.status`/`cause.messageCode` to the response and includes stack/cause only when `NODE_ENV !== 'prod'`.
- **i18n via numeric message codes**: every user-facing string is a code looked up in `src/lang/en.json` and `src/lang/ar.json` through `chooseLanguage({ lang, code })`, chosen from the `Accept-Language` header. When adding a new message, add the code to **both** JSON files. Success responses go through `sendSuccess({ res, statusCode, messageCode, lang, data })` → `{ success, message, data }`.
- **Validation**: DTOs export functions `(lang) => ({ body, params, query })` of Zod schemas so error messages are localized. `validationPipe({ schema })` parses and replaces `req.body`, and exposes `req.validated`; failures return **409** with messageCode 201 and the Zod issues in `extra`.
- **Auth**: JWTs are signed with a secret chosen by role (`aud`: USER/ADMIN) and token type (access/refresh) — see `getTokenSignature`. On login, `setCacheToken` stores each token's `jti` in Redis under `getRevokedTokenKey`, and `decodeToken` rejects any token whose key is *missing*, so despite its name the key works as an allowlist. Logout and token rotation revoke by *deleting* keys (`revokeToken` in `tokenSecurity.js` sets the key instead, which would not revoke anything; it is currently unused). `authenticationGuard()` sets `req.user` / `req.payload`. Google sign-in verifies an ID token server-side with `google-auth-library`.
- **Uploads**: `localFileUpload({ validation, customPath, maxFileSize })` writes to `server/assets/<customPath>` (served publicly at `/assets`, gitignored); its filter only sees the client-declared mimetype, so always follow it with `verifyUploadedFiles({ validation })`, which checks the saved files' magic bytes and deletes the request's files on mismatch. Attachments are stored as file paths on the document.
- Messages from logged-in senders store `senderId`, but read queries use `select: '-senderId'` to keep the sender anonymous to the receiver.
- **Conversations (no websockets, clients poll)**: `Conversation` holds exactly two `participants` (`{ userId, lastReadAt, unreadCount }`) plus a denormalized `lastMessage`; `participantKey` (sorted ids) is unique so a pair has one conversation. `ConversationMessage` is a separate collection from the anonymous `Message`. Unread counters are maintained with `arrayFilters` updates (`participants.$[me]` / `$[other]`) when sending, reading and deleting — keep them in sync if you add new write paths. Polling cursors: `GET /conversation?since=<serverTime>` (relies on `updatedAt` bumping on every conversation write) and `GET /conversation/:id/messages?after=<messageId>` (ObjectId order); `before=` pages backward through history.

## Client architecture

Next.js 16 App Router, React 19, TypeScript, Tailwind v4, shadcn/ui (on `@base-ui/react`), `sonner` toasts, `next-themes`. Path alias `@/*`.

- `lib/api.ts` — all REST calls to the Express API, the shared response/entity types, and localStorage token helpers (`saraha_access_token`, `saraha_refresh_token`, `saraha_lang`).
- `lib/auth-context.tsx` — client-side `AuthProvider`: current user, language + translations (`lib/translations.ts`, en/ar), and the open/closed state of global dialogs (auth modal, settings, QR).
- `app/api/auth/[...nextauth]/route.ts` — NextAuth (JWT sessions) with a credentials provider that proxies to `/authentication/login` and an optional Google provider (enabled only when `GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET` are set; must match the server's `OAUTH_GOOGLE_CLIENT_ID`).
- Pages: `app/page.tsx` (landing), `app/dashboard/page.tsx` (inbox), `app/u/[identifier]/page.tsx` (public profile / send message). Feature components live in `components/<feature>/`, shadcn primitives in `components/ui/`.
